## THE SYNC FILE

### Location

`.mind/state/SYNC_Project_State.md` — single file, ~200 lines max.

### Format

Markdown with a fixed section order (see ALGORITHM for full specification):

```markdown
# Project — Sync: Current State

```
LAST_UPDATED: {YYYY-MM-DD}
UPDATED_BY: {agent name or "human"}
```

## CURRENT STATE          ← what the project is
## KEY COMPONENTS         ← module table (path, status)
## ACTIVE WORK            ← in-progress initiatives
## RECENT CHANGES         ← last ~5 events (newest first)
## DEPLOYMENT             ← infra summary
## KNOWN ISSUES           ← active problems table
## HANDOFF: FOR AGENTS    ← technical context
## HANDOFF: FOR HUMAN     ← executive summary
## TODO                   ← 3 tiers: Immediate / High / Backlog
## MODULE COVERAGE        ← code vs docs completeness
```

### Conventions

| Convention | Rule |
|------------|------|
| Header fields | `LAST_UPDATED` must be a parseable `YYYY-MM-DD` date |
| RECENT CHANGES | Max 5 entries, newest first, each with What/Why/Impact |
| KNOWN ISSUES | Table format: description, severity, area, notes |
| TODO tiers | `Immediate` → `High Priority` → `Backlog` |
| Line budget | ~200 lines total; prune aggressively |
| Status markers | `Stable`, `New`, `Fixed`, `Low`/`Medium`/`High`/`Critical` |

## WHO MAINTAINS THE SYNC FILE

There is no automated writer. The SYNC file is maintained by **agents and humans** following the procedures in ALGORITHM_Project_State.md:

| Actor | When | What They Do |
|-------|------|-------------|
| Agent (session start) | Beginning of work session | Reads SYNC for orientation |
| Agent (session end) | After producing changes | Updates RECENT CHANGES, KNOWN ISSUES, TODOs, header |
| Agent (audit) | When flagged by sync_freshness check | Runs staleness audit procedure |
| Human | After significant decisions | Updates HANDOFF: FOR HUMAN, ACTIVE WORK |
| `mind work` | On run | Generates `REPAIR_REPORT.md` (separate file) |

## INTEGRATION POINTS

### Reads From

| Source | What | Why |
|--------|------|-----|
| Git history | `git log`, `git diff` | Ground truth for RECENT CHANGES verification |
| Filesystem | Directory listings, file existence | Ground truth for KEY COMPONENTS, MODULE COVERAGE |
| Code files | `**/*.py` status | Module maturity assessment |
| Doc chain files | `OBJECTIVES`, `PATTERNS`, etc. | MODULE COVERAGE accuracy |

### Read By

| Consumer | How | Why |
|----------|-----|-----|
| Every agent at session start | Direct file read | 60-second orientation |
| sync-state health checks | Regex parse of `LAST_UPDATED` | Staleness detection |
| `mind status` CLI | File read + parse | Status display |
| Other SYNC files | Cross-reference | Module dependency tracking |

## BOUNDARIES

### What This Module Owns

- The `.mind/state/` directory and all doc chain files within it
- The conventions governing SYNC file format and update procedures
- The definition of what "fresh" and "stale" mean for project state

### What This Module Does NOT Own

- **Per-module SYNC files** (`docs/**/SYNC*.md`) — owned by their respective modules
- **sync-state capability code** (`.mind/capabilities/sync-state/`) — owned by the capability system
- **Git history** — SYNC is a curated view, git is the archive
- **Task management** — SYNC tracks TODOs for orientation only; graph task nodes own execution
- **`REPAIR_REPORT.md`** — generated by `mind work`, not by the SYNC procedures
